`CniInstallation` gained `spec.calico.bgp` (BGPConfiguration + peers) and `spec.calico.loadBalancerPools[]`, and pod pools are now rendered as explicit `crd.projectcalico.org/v1` `IPPool`s, so the full Flux `applications/calico/controlplane` IPv6-only setup is expressible. Spec: `docs/superpowers/specs/2026-09-19-ipv6-only-calico-design.md`; plan: `docs/superpowers/plans/2026-09-19-ipv6-only-calico.md`; live acceptance: `docs/runbooks/ipv6-only-kvm-verification.md`. Dual-stack is deliberately a future spec (address family is inferred from CIDRs, so relaxing the mixed-family check needs no API break).

**Non-obvious facts that drove the design (verified by rendering the charts, not assumed):**
- The tigera-operator chart **v3.29.1 ships 24 CRDs; v3.32.1 ships none.** From 3.32 the running operator creates every CRD (including all `crd.projectcalico.org` ones). Applying `Installation` right after the operator Deployment fails discovery with `Missing Kind` on 3.32, so the reconciler waits for each custom resource's kind via `apply::wait_for_kind_available` (180s, `timeout_at`-wrapped per [[wait-for-crd-established]]). The old `wait_for_crd_established` only helps chart-shipped CRDs.
- The operator skips creating pools from `Installation` when any `IPPool` exists (bring-up failure "no configured Calico pools"). Pod pools are therefore explicit objects **and** passed to `Installation` with the **same `name`**, so the operator adopts one pool instead of creating a duplicate. `IPPool` is one kind used by both pod and LB pools, so ordering is explicit phases in `reconcile`, not `rank_for_kind`.
- Calico's `IPPool.spec.cidr` is immutable: renumbering is a new-pool swap; retired pools stay declared with `disabled: true`.
- `blockSize` default is family-dependent (26 v4, 122 v6), so it is optional in the CRD and resolved at render time.

**Live-verified 2026-09-21 on a KVM Talos cluster (runbook steps 2-6 all pass):** clean installs end with exactly the declared pools (no operator duplicate), `flexVolumePath: None` is accepted by the 3.32.1 Installation CRD, BGP establishes, LB VIPs are advertised as the pool `/112` and reachable, and pod egress is SNAT'd. Two things only live testing found: (1) **cleanup deadlocked** because on v3.32.x the operator's `Installation` carries `apiserver-controller`/`goldmane-controller` finalizers that wait for `APIServer`/`Goldmane` to go, while cleanup deleted `Installation` first and waited; fix is `custom_resource_cleanup_order` (Installation last) plus issuing all deletes before any wait. (2) The operator **recreates a deleted pod pool** about a second later while `Installation` still exists, so cleanup ends with `calico_group_sweep`, a second delete of the Calico-group objects after the operator resources are gone. The controller image must include the Calico phases before the CR is applied, or the operator creates its own `default-ipv6-ippool` and no BGP peer or LB pools appear (`deploy/bootstrap.yaml` points at `:latest`, which can lag the branch). Environment prerequisites (in the runbook): the gateway needs the peering VLAN, bridge and peer address; the hypervisor port needs an ingress rule per LB port and the LB CIDRs as allowed address pairs; a second NIC breaks VIP replies through asymmetric routing. CoreDNS is not restarted by cleanup: its pods keep stale pod IPs after Calico is removed (open question whether the controller should restart it).

**Deliberately not done / still open:** chart hardening annotations and image digest pinning from the Flux app; readiness gating on `calico-node`. `status.appliedResources` is only written after every phase succeeds (pre-existing), so if a first install fails partway (e.g. `KindNotAvailable`) and the CR is deleted, cleanup sees an empty ledger and may leave the `tigera-operator` namespace, RBAC and Deployment behind; remove them by hand. LB IPPools are written directly to `crd.projectcalico.org/v1` with only cidr/allowedUses/nodeSelector/disabled (no ipipMode/vxlanMode/natOutgoing/blockSize, unlike pod pools); the stored object is confirmed in runbook step 2. Cleanup deletes Calico-group objects without a removal wait and sweeps them again after the operator resources are gone (a pool left over despite that, e.g. with `cleanupTimeoutSeconds: 0`, must be removed by hand). The cluster used for the example addressing must use a different AS and prefixes than any other cluster peering with the same gateway (placeholders: AS 64514, `fd00:db8:0:*`).

**Upgrade ordering:** apply the new `deploy/crd.yaml` BEFORE rolling the controller image. The old CRD persisted a `blockSize` default of 26 into stored objects, so an existing IPv6 `CniInstallation` that omitted `blockSize` will read back 26 and now fail validation with `BlockSizeOutOfRange` (it was already invalid for the operator); set `blockSize` explicitly, e.g. 122.

**How to apply:** when bumping the Calico chart version, re-render it (`helm template ... --include-crds`) and check whether CRD shipping changed before trusting the apply ordering; the ignored test `helm::tests::v3_32_1_chart_ships_no_crds` pins the current behavior.
